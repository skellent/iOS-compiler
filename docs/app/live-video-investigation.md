# Phone-camera live video for Panic Button — investigation

This document records the investigation before the SOS recording implementation. The TikTok-first recorded-video flow and its required setup are now documented in [backend/docs/sos-video-setup.md](../../backend/docs/sos-video-setup.md). Facebook and Instagram findings below remain research only.

Research date: 2026-09-15. This is a feasibility and implementation investigation, not an implemented feature. Platform approvals and account eligibility must be tested with real accounts before committing to a release.

## Executive decision

For an **ordinary user's personal Facebook timeline**, Live is conditionally feasible: a current mobile broadcaster describes Facebook Login and timeline streaming, and Meta documents a User `live_videos` edge. This still requires a test of current app-review permission, account eligibility, and audience behavior; it is not available merely because the user linked a Facebook login. Meta also exposes Page Live, but Pages are outside this product's main requirement. The phone still needs to capture camera **and microphone**, encode the media, and send it to an RTMP/RTMPS ingest URL. The Graph API alone does not transmit camera frames.

Instagram has an official *Live Producer* workflow for eligible professional accounts: obtain a temporary stream URL/key from the Instagram desktop live setup, send media with an encoder, preview it, and explicitly start the broadcast in Instagram. Meta's public Instagram API documents publishing uploaded media/Reels, not creating or controlling a Live broadcast. A Panic Button integration can therefore offer a manual RTMP destination, but cannot promise a one-tap, fully automated Instagram Live flow.

TikTok's public Content Posting API uploads or publishes **finished files**, not live camera streams. TikTok LIVE exists in its app and LIVE Studio; access to a third-party encoder or stream key is account-specific. Treat TikTok streaming as an optional manually provisioned/partner destination, not as a public API integration available to every user.

For **saved recordings**, the situation is different. TikTok's Direct Post API supports OAuth-authorized posts to an ordinary user's profile, with app approval/audit and explicit user consent for the post. Facebook personal-profile recorded-video posting should use Facebook's native share composer/system share flow; Meta's current official Facebook Reels API examples are Page-token based, so do not promise silent personal-profile API uploads. Instagram's public API excludes personal consumer accounts; a user can still export a file to Instagram's app and choose to publish there. A user willing to switch their Instagram account to **Creator or Business** can connect through the Instagram Login API and publish supported recorded media without creating a Facebook Page.

Because this is an emergency app, social broadcasts should be optional and must never hold up the existing alert and location delivery. Public platform lives also expose the incident and possibly the user's location to an audience beyond the emergency contacts. A private video link for confirmed contacts is the better default if the product goal is evidence and contact awareness; Facebook can be an opt-in destination.

## What this repository currently has

- [`app/src/views/home.ts`](../../app/src/views/home.ts) creates an alert after a 1.4-second hold, obtains GPS, and starts a 60-minute location tracker. The alert's delivery is already asynchronous. There is no video preview, video state, or live-video endpoint.
- [`app/src/lib/liveTracking.ts`](../../app/src/lib/liveTracking.ts) publishes GPS over WebSocket. That protocol sends coordinates; it is not a media transport.
- [`app/package.json`](../../app/package.json) declares Capacitor 8 and `@capacitor/camera`. Capacitor's Camera API can take photos, select saved media, and record a **finite video file**; it does not provide a continuous RTMP publisher.
- [`backend/main.py`](../../backend/main.py) sets `Permissions-Policy: geolocation=(), microphone=(), camera=()` on responses, including the remotely loaded `/app` UI. This blocks a WebView `getUserMedia()` prototype until the policy permits `camera=(self), microphone=(self)` on the app origin. `getUserMedia()` also requires a secure context, so the production app URL must use HTTPS.
- [`app/android/app/src/main/AndroidManifest.xml`](../../app/android/app/src/main/AndroidManifest.xml) has location permissions but no declared camera/microphone foreground service for continuous native capture. `app/ios/` is not present in this checkout, so Android is the concrete first target.
- [`docs/app/architecture.md`](architecture.md) explains the remotely loaded WebView. A JS/CSS interface change can deploy with the backend; new native capture/service permissions require a Capacitor sync and new binary.

| Instagram personal consumer account | **No supported app integration found.** The normal Instagram mobile app can go Live with its own camera if account eligibility allows; Live Producer's external encoder path is for eligible professional accounts. | **User-completed share.** Export an MP4 through the Android share flow to the Instagram app; user edits/chooses the destination and publishes. “Connect channel” must therefore mean a **capability check**, not a uniform OAuth promise. Facebook Live, Instagram recorded publishing for professional accounts, and TikTok recorded Direct Post require distinct permissions. Normal Instagram accounts and personal Facebook recorded posts should show an **Export to app** action, not a misleading “automatic publishing” switch. Social platform limits also mean the app cannot guarantee that an emergency trigger silently starts three Lives or posts a recording without user action.

## Two phone capture architectures

### A. WebView prototype and server relay

`getUserMedia({video: {facingMode: "environment"}, audio: true})` gives a preview and `MediaStream`. `MediaRecorder` makes short encoded chunks. A dedicated authenticated WSS ingest endpoint receives binary chunks and a relay process (such as FFmpeg) converts the container/codecs as needed to H.264/AAC/FLV and publishes over RTMPS. This can make a quick Android proof of concept and a private contact stream, but production must verify actual Android WebView encoder MIME support, A/V sync, latency, pause/resume, and upload loss. The backend's current policy has to change for `/app` and HTTPS has to be in place. Browser MediaRecorder output may be WebM/Opus, so a remux/transcode step is likely; do not assume that declaring `video/webm;codecs=h264` works on every phone.

Separate the media relay from the FastAPI alert workers. A 2 Mbps feed is roughly **0.9 GB/hour** of phone upload, before protocol overhead; 3 Mbps is about **1.35 GB/hour**. Each social destination adds relay outbound traffic. The location WebSocket and video ingest require separate scaling, quotas, and failure handling. The relay must accept only server-issued session IDs and preapproved platform hostnames; it must never accept an arbitrary user-supplied FFmpeg output URL or log stream keys.

### B. Native Android broadcaster (preferred for a reliable release)

A Capacitor plugin can start Android camera/audio capture, a hardware H.264 encoder and AAC audio encoder, and a native RTMPS publisher. It can expose `start`, `stop`, health, camera switching, and bitrate state to the WebView. This avoids WebView codec and background-timer variability and can connect directly to Facebook or a controlled relay. It requires a native SDK/library evaluation, manifest permissions, a new APK, and device testing. If capture is intended to continue when the app loses focus, start the appropriate camera/microphone foreground service while the Activity is visible and follow Android 14+ foreground-service type/permission rules. **Do not promise screen-off or background camera streaming** until tested; Android's camera/microphone while-in-use rules and OEM behavior can prevent it. iOS later needs a separate AVFoundation capture/publisher implementation and lifecycle design.

For multi-destination delivery, prefer **phone -> one authenticated relay -> Facebook / manual Instagram / approved TikTok / private contact playback**. This spends upload bandwidth once and lets each destination use its own resolution/key. Direct-to-Facebook native RTMPS is a smaller initial pilot if only one destination is needed.

## Proposed product and backend flow

1. User opts into camera broadcasting and selects destinations **before** an emergency. Connect their personal Facebook account with an authorization-code flow, request only approved Live permissions, and verify that their **timeline** is a permitted target. Store tokens encrypted server-side. Do not place long-lived tokens or social stream keys in the remote WebView bundle.
2. The hold-to-alert path continues to create the alert and start GPS immediately. Start video in parallel only if the user enabled it and camera/mic permission is available. Show a clear live indicator and a separate stop-video control; a video failure must leave GPS sharing and notifications active.
3. For Facebook, backend creates a scoped live-video session for the user's **personal timeline** if Meta grants the required capability, captures its `id` and `secure_stream_url`, gives the phone/relay a short-lived ingest credential, and monitors state. Publish only when the feed is actually healthy. Stop and reconcile on app stop, timeout, disconnection, or user action.
4. For Instagram, allow the user to paste the Live Producer URL/key for the **current** broadcast into a short-lived protected session, then direct them to complete the Instagram Go Live action. The UI must make the manual step unmistakable. Never request Instagram passwords or scrape private endpoints.
5. TikTok LIVE appears only when a user has a supported encoder destination or a formal partner integration. Otherwise, provide a link to open TikTok's own LIVE flow; that uses TikTok's camera, not this app's feed. For a completed recording, offer TikTok Direct Post after app audit and explicit user post consent, or Share Kit as a user-completed alternative.
6. For Facebook/Instagram completed recordings on ordinary personal accounts, export the MP4 to the platform's native composer and explain that the user must finish posting. Instagram Creator/Business accounts may additionally use its Content Publishing API without a linked Facebook Page.
7. If contact video is required, introduce a private viewer URL and a playback service (for example WebRTC or LL-HLS), independent of social-platform broadcasts. The existing short location token is **not automatically** a suitable video token; decide access, expiry, revocation, retention, and replay policy explicitly. Contact messages can include the video URL once it is genuinely live.

## Work order and go/no-go gates

1. **Facebook personal-account/API gate:** using a test Meta app and eligible **personal timeline**, verify actual Graph version, permissions/app review, create response, RTMPS feed, audience/preview/publication, permalink, and stop semantics. No code architecture can remove a platform denial. Pages are optional and not a substitute for this gate.
2. **Android media spike:** with HTTPS and app-page camera/mic policy enabled in a test environment, measure `getUserMedia` and `MediaRecorder` support on several real phones; test a 10-minute relay to a private RTMPS endpoint. Compare this with a native capture pilot before choosing A or B.
3. **Emergency behavior:** ensure the alert is sent first, camera permission can be denied without blocking it, GPS/video stops are independent, and reconnect cannot accidentally start a second public broadcast. Add visible consent and privacy controls.
4. **Production relay:** enforce authentication, destination allowlist, backpressure, one session per alert, process/resource quotas, encrypted secret storage, cleanup, and measurable ingest/egress health. Test weak mobile upload, app backgrounding, network handoff, and backend restart.
5. **Instagram/TikTok gate:** test eligible accounts and record whether Live Producer/encoder keys actually exist for intended users; keep these optional until access is confirmed.
